Group A · findings 1–2 · blocking

The release gate must be real

Both blocking findings here are about trust: a gate that doesn't gate, and a status file nothing ever refreshes. Together they decide what “release-safe” means in this plan.

flowchart LR T["Tag v1.2.3 pushed"] T --> I["i18n.yml (separate workflow)"] --> R["reports translation health"] T --> A["android.yml"] A --> C["check job"] C -->|"needs: check"| B["build job"] B --> P["Publish GitHub Release"] R -.->|"failure here does NOT stop this path"| P A -->|"fix: run validators here"| C

The dashed line is the gap: the tag-triggered i18n workflow runs in parallel and its failure never blocks publishing. The release waits only on android.yml's own check job.

01The proposed tag trigger would not gate a releaseBlocking→ D1

In plain English

Adding push.tags: ['v*'] to i18n.yml starts a second workflow that runs in parallel with android.yml. Workflows don't wait for each other. The review's proposed gate therefore gates nothing.

Evidence · verified

✓ i18n.yml's trigger block is at line 15 (on: → pull_request + workflow_dispatch only; no tags today).

  • android.yml:68 — build: needs: check: the release only waits for its own check job.
  • android.yml:226–227 — Publish step gated on the tag alone.

Required change

Run at least validate_strings.py --release and gen_supported_locales.py check inside android.yml's check job. Then the existing build.needs: check is a real gate. Keep a tag-triggered i18n.yml only if you want a parallel report; it is not a substitute.

02translation_status has no ongoing writer or provenanceBlocking→ D2

In plain English

The snapshot says “this key is approved” but nothing checks whether the English text or the translation changed after that approval. And because Android XML drops Weblate's richer review state, Weblate can't refresh the snapshot through its normal commits. The file would age into stale metadata.

Evidence · verified

✓ validate_strings.py:285 _load_translation_status() reads key → state; line 324 rejects any state outside {translated, approved}. No source or translation hash is stored.

  • ✓ Status keys are only checked against known source keys — not against the text they approve.
  • ✓ Today the file covers only en-GB (the regional override), so this is inert — until the seed grows it to 20 locales × ~1,500 keys with no writer.

Required change

Pick one: (a) drop it from the release path — gate on key presence + structural validity (the policy already agreed: malformed fails, missing passes); or (b) keep it with source + translation hashes, a defined Weblate export path, per-file schema, legacy migration, and an acceptance test proving a source-text edit fails until status refreshes. Splitting the file fixes reviewability, not correctness.

Group B · findings 3–5, 7 · blocking + major

The seed pipeline needs mechanical fixes

The one-off Claude batch is where translations are actually produced. These findings are about the batch request shape, the glossary, XML escaping, and the money math — all verifiable, all fixable before a single request is sent.

flowchart LR S["values/*.xml · 6 files · 1,537 resources"] --> CH["41 chunks per locale · 40 keys each"] CH --> B["One batch · ~820 requests for 20 locales"] B --> M["Run manifest: batch ID ↔ sanitized request IDs"] M --> ST["Stage whole locale in temp dir"] ST --> V{"All six files validate?"} V -->|"yes"| PUB["Publish locale files atomically"] V -->|"no"| RET["Retry from manifest · resumable, no re-buy"]

The corrected pipeline: per-file chunking yields 41 chunks per locale (not 31), a persisted manifest makes collection resumable, and a locale is published only after every one of its six files validates.

03The proposed protocol glossary would corrupt translationsBlocking→ D3

In plain English

safe_literals.txt is a record of where a literal appears, not a dictionary of words that must never be translated. Its protocol category alone has 1,129 entries — including name, on, one, tr, turkey, three. Treating those as global exclusions leaves ordinary UI sentences half-English.

Evidence · verified

✓ tools/i18n/safe_literals.txt — 3,769 lines; header (line 1) documents the <count>\t<category>\t<path>\t<literal> schema; path-scoped by design.

  • ✓ name, on at lines 249–251 (CompanionHttpProtocol.kt); one at line 1201 (EpgMatcher.kt); tr/turkey at 1233–1234.

Required change

Seed the glossary from explicitly reviewed immutable tokens only — product/brand and protocol constants. And because “translate consistently” is not enforceable across independent batch requests, add a per-locale terminology pre-pass that chooses target terms once and injects that frozen table into every chunk for that locale.

04The documented Batch API request shape contains an invalid ID and an underspecified schemaBlocking

In plain English

custom_id = "<languageTag>|<file>|<chunk-index>" is rejected out of the box: batch IDs permit only alphanumerics, _, and -, max 64 chars. Separately, a per-chunk schema that enumerates ~40 keys as properties (some plural unions) can exceed Anthropic's 16-union structured-output limit, and any per-chunk schema change invalidates prompt caching.

Evidence · verified

✓ The |-separated ID is invalid per Anthropic's batch docs (alphanumerics / _ / -, ≤64 chars).

  • ✓ The 16-union structured-output limit and schema-change cache invalidation are documented in Anthropic's structured-output docs.
  • ✓ Structured outputs can still be incomplete on max_tokens or nonconforming on refusal.

Required change

Sanitized IDs like de-strings-settings-0001, with the exact ID→input mapping persisted in the run manifest. Use a stable, small array schema — separate fixed schemas for strings and plurals — and validate keys, counts, quantities, and ordering locally. Handle stop_reason, not only result.type.

05The XML write order would destroy <xliff:g> markupBlocking

In plain English

“Reinsert the original elements, then escape < to &lt;” applied literally turns <xliff:g> into visible text. The tokens the whole pipeline exists to protect become the thing users see.

Evidence · verified

✓ The source carries meaningful paragraph breaks and Android escapes that a text-only pass can silently convert, drop, or double:

  • ✓ strings_settings.xml:885 — settings_low_zoom_warning: …\n\nPress OK… plus two <xliff:g> elements.
  • ✓ strings_player.xml:356 — player_subtitles_account_needed: \n\n and \u2192.

Required change

Escape translated text nodes first, then insert protected XLIFF nodes — or serialize a mixed-content XML tree. Never globally escape the completed element body. The token layer must protect \n and \uXXXX escapes, not only format specifiers; self-validation alone will not catch these.

07The batch arithmetic is wrongMajor

In plain English

At 40 entries per file-scoped chunk, the six live files produce 41 chunks per locale, not 31 — about 820 requests for 20 locales. The pilot plus full rollout also means at least two batch submissions, not one, before retries.

Evidence · verified

✓ Counted translatable resources per file (strings + plurals + arrays):

  • strings.xml 95 → 3 chunks
  • strings_setup.xml 119 → 3
  • strings_settings.xml 188 → 5
  • strings_player.xml 204 → 6
  • strings_content.xml 260 → 7
  • strings_features.xml 671 → 17
  • Total 1,537 resources · 41 chunks · ×20 = 820

Required change

Persist a run manifest: batch ID, model, source hash, prompt hash, requests, results, retry lineage. Collection must be resumable without paying for another submission. Stage a whole locale in a temporary directory and publish only after all six files validate.

Group C · findings 6, 10 · blocking + major

You can't pilot or measure as written

Two execution-order problems: the pilot languages never reach the APK, and the “before” APK measurement is scheduled after the state it should measure has already changed.

06The pilot cannot be walked on-device while its locales remain unpackagedBlocking→ D4

In plain English

German, Arabic, and Japanese are packaged: false in the catalogue. Gradle's localeFilters only keeps packaged == true qualifiers, and the picker only shows packaged + visible locales. Build the pilot APK and de/ar/ja simply aren't in it — there is nothing to walk.

Evidence · verified

  • ✓ locales.json — de, ar, ja all packaged: false, pickerVisible: false.
  • ✓ app/build.gradle.kts:143 — localeFilters.addAll(packagedLocaleQualifiers).
  • ✓ Phase 2 doc — picker shows only packaged AND pickerVisible rows.

Required change

An explicit pilot QA mechanism: a debug-only Gradle property adding pilot qualifiers (recommended — release policy untouched), or a local uncommitted catalogue flip reverted after QA. Either way, inspect the pilot APK to prove all three locale configurations are present before device testing starts.

10APK measurement occurs too lateMajor

In plain English

Execution step 8 can't produce a clean “before flip” measurement after step 5 already flipped the catalogue. And the existing baseline is an older Phase 0 measurement — useful history, but not a same-branch before/after pair.

Evidence · verified

  • ✓ docs/i18n-apk-size-baseline.md:30 — “Phase 0 baseline (standard release, unsigned)”, an earlier filtered build.
  • ✓ The plan's step 5 flips the catalogue before step 8 measures both sides.

Required change

Capture the pre-flip release immediately before the catalogue change, then the post-flip release after it — same commit context, toolchain, signing mode, and clean-build conditions. Otherwise unrelated code and signing differences contaminate the delta.

Group D · findings 8–9 · major

Shared infrastructure before the flip

Two consolidation findings: one coverage calculator for everyone, and a Weblate generator contract that is actually derivable and checkable.

08Coverage still would not be “structurally the same number”Major

In plain English

The validator and the generator each keep their own parser and key-set implementation. The generator's own docstring says it “must match validate_strings.py's suffix scheme exactly” — that's a drift risk already. Adding a third “identical” calculation to --report multiplies the places where a future change can split the numbers.

Evidence · verified

  • ✓ validate_strings.py:80 — _parse_dir() (suffixed keys, its own entry model).
  • ✓ gen_supported_locales.py:35 — _string_keys(), a separate implementation with a comment demanding they stay in sync.

Required change

Extract shared resource inventory and coverage functions into one module used by both tools (and the seed runner). Define the JSON report schema, rounding, stdout behaviour, and exit behaviour on invalid resources once, in that module.

09The Weblate generator contract is incomplete and “exactly seven aliases” is not derivableMajor

In plain English

Under the discovery regex (which captures the directory segment after values-), the catalogue has eight qualifier/code mismatches, including pt-rPT → pt_PT — and the proposed seven omit exactly that pair. Android-style codes may be recognized natively, but then the generator needs an explicit normalization rule and tests, not an unexplained exception. The plan also never names what gen_weblate_config.py check compares against.

Evidence · verified

✓ Captured segment vs weblateCode mismatches in locales.json:

  • en-rGB → en_GB, pt-rPT → pt_PT, pt → pt_BR, zh-rCN → zh_Hans, zh-rTW → zh_Hant, nb → nb_NO, es-rUS → es_419, es → es_ES
  • ✓ Hosted Weblate's recommended GitHub App flow already handles notifications and PR access — normally no separate manually-configured webhook. The Android format's Java-format checking is a format-provided quality check, not an addon to install.

Required change

Define an explicit normalization rule with tests for all eight pairs. Name the checked-in generated output that check compares — a dedicated generated config file or generated markers inside the setup document. Follow Weblate's GitHub App guidance in the checklist.

The conclusion, sequenced

Recommended execution order

Adopting the five decisions above (recommended options) makes this the plan of record. Gate and infrastructure land before any locale is flipped or measured.

1.Shared resource/coverage module; split + hash-bind (or drop) translation status; define the empty allowlist; add --report; test all migrations.
2.Wire the real release gate into android.yml's check job.
3.Implement the safe curated glossary and the resumable, atomic seed runner with stable schemas and persisted manifest.
4.Run the three-locale pilot (de/ar/ja) with an explicit debug packaging procedure; verify the APK contains them first.
5.Run the remaining locales.
6.Generate Weblate configuration, complete the hosted setup (GitHub App flow), and verify a no-surprise repository round trip.
7.Measure the pre-flip APK, then atomically land statuses, catalogue flips, generated Kotlin, and the post-flip APK measurement.
8.Run the listed automated and device verification, including negative gate tests.
