OwnTV · i18n Phase 4 review

The translation plan is close, but its definition of “safe” needs changing.

The original plan assumes every packaged language must be 100% translated. Your actual goal is different: ship partial languages safely, show the honest progress, and let English fill every gap.

The important branch is in the middle: incomplete is allowed; invalid is not.

Android fallback

“Missing” must mean the key is absent

Android falls back one resource at a time. A German file can contain 900 translated keys and omit the rest; omitted keys come from the complete English values/ resources.

Key absent

Android displays English. Weblate sees untranslated work. Coverage goes down. This is the correct representation.

Empty key present

Android can display nothing. It does not mean “please use English.” Do not use empty values as placeholders.

English copied into German

The app looks like it fell back, but tools may count the key as translated. The percentage becomes misleading.

Group 1 · product and CI policy

Concerns about what is allowed to ship

These are the most important changes because they decide whether ordinary development can continue after translation support is enabled.

01The 100% coverage gate contradicts your release policyMust change

In plain English

The plan would refuse a pull request whenever a packaged language is missing even one new translation.

Why it matters

Every new English label would require 20 simultaneous translations. That recreates exactly the bottleneck you said you do not want.

Plan correction

Remove the Tier 1 “must be 100%” failure. Missing keys become a report and a lower percentage, never a failure.

02Release time should report translation status, but never block the releaseMust change

In plain English

A release should say “German is 96%, Arabic is 83%,” so the maintainer knows the current state. That report is information, not a permission check.

What the repo should do

The existing PR workflow can continue checking translation structure. The release workflow can run a read-only coverage report and put it in the release job summary.

Plan correction

Add a non-blocking release-time report step. It must not require 100%, must not create or publish a release, and must not turn missing translations into a failure.

03An empty-translation allowlist works against English fallbackMust change

In plain English

An empty translated value is a real value: it can render as blank. Android only reliably falls back when the translated key is missing.

How Weblate knows

Weblate has the complete English values/ file as its base. If save exists in English but is absent from values-de/, Weblate sees that ID as untranslated. No empty German entry is needed.

Plan correction

Keep empty translations invalid. Omit unfinished keys. The missing key is both the Android fallback signal and Weblate’s open translation task.

04“Needs editing” must not block releases eitherMust change

In plain English

The current status loader treats anything except translated or approved as an error.

Why it matters

Your new policy says incomplete translation work is visible but non-blocking. A Weblate “needs editing” flag is unfinished work, not broken app code.

Plan correction

Report unfinished states separately. Fail only when an included translation is structurally unsafe. Do not call unfinished content “release unsafe.”

05A JSON report is not automatically visible to a humanShould fix

In plain English

Printing machine-readable JSON into a long CI log is like putting a warning on page 80 of a manual.

Useful output

Show a small PR summary: German 96% · 57 missing, Arabic 83% · 261 missing, and so on.

Plan correction

Keep --report json for tools, but also write a Markdown table to GitHub’s step summary and list newly missing keys in the log or artifact.

06The percentage needs one shared calculatorShould fix

In plain English

If CI and the picker each do their own counting, they can eventually disagree even if both implementations looked correct on day one.

Example

One side might count a plural as one key while the other counts each plural form. Users could see 93% while CI reports 94%.

Plan correction

Move source-key discovery and coverage calculation into one small shared Python module. Both validator reporting and Kotlin generation call it.

07An untouched locale currently becomes “—”, not 0%Clarify

In plain English

-1 means “we do not have a translation snapshot.” The picker turns that into “—”, which means “unknown,” not “zero.”

Why that is confusing

If Arabic has 0 translated keys out of 1,537, the math is known: 0 ÷ 1,537 = 0%. Showing “—” hides useful information from the user.

Plan correction

For every visible translation target, show 0% when its directory has no translated keys. Keep “—” only for a locale that is deliberately not a translation target.

Group 2 · one-off AI seed

Concerns that could make the batch fail or corrupt output

The core idea—keep XML away from the model—is good. These details need adjustment so that good idea survives contact with the API and filesystem.

08The proposed batch request ID is rejected by the APIMust change

In plain English

The plan uses IDs such as de|strings|0. Claude Batch IDs do not allow the | character.

What is allowed

Only letters, numbers, hyphens, and underscores, with at most 64 characters.

Plan correction

Use a safe ID such as de_strings_000, and unit-test the ID format before submission.

09The request estimate is about 820, not 620Correct math

In plain English

The six files contain 95, 119, 188, 204, 260, and 671 translatable resources. At 40 per request, file boundaries produce 41 requests per locale.

Total

41 × 20 = about 820 initial requests, before retries. This is still well below the API limit.

Plan correction

Fix the count and make the cost estimate a measured dry-run output rather than a hard-coded planning promise.

10A different 40-key JSON schema per request is fragileMust change

In plain English

If every string key becomes a property in the output schema, every chunk has a new, complex schema. Plural values also create many string-or-object unions.

Why it matters

Claude enforces schema-complexity limits, and changing the schema invalidates the structured-output and prompt caches.

Plan correction

Use one stable schema: a list of records containing key and a list of quantity/text values. Validate the exact expected keys in Python afterward.

11Seed cost optimization is out of scope by decisionDe-scoped

Decision

This is a one-time seed operation. Do not spend plan complexity on squeezing every possible cache discount out of it.

What still matters

Keep the prompt deterministic and keep the batch correct. That makes retries and debugging easier, regardless of the final bill.

Plan correction

Remove cost ceilings, cache tuning, and cost reporting from the acceptance criteria. The maintainer has already accepted the one-time seed expense.

12The protocol allowlist is not a safe global “never translate” glossaryMust change

In plain English

safe_literals.txt records source-code literals in a particular file and context. It contains ordinary words such as “name,” “on,” “password,” “server,” and “true.”

Why it matters

Telling the model to never translate those words anywhere can leave normal user-facing sentences partly English.

Plan correction

Create a small, human-curated glossary for actual product names and protocol terms. Do not import the whole path-scoped protocol category.

13Reinserting XLIFF tags and then escaping “<” destroys the tagsMust change

What is an XLIFF tag?

It marks a variable inside a sentence. For example: Welcome, <xliff:g id="name">%1$s</xliff:g>. The variable is supplied by the app; the translator may move it, but must not translate it.

In plain English

The plan says to put the tag back into the text and then escape every less-than sign. That turns a real XML element into visible text.

Plan correction

Give the serializer the text pieces and the real XLIFF node separately. It escapes ordinary text, but leaves the placeholder element as XML. Preserve Android escapes such as \n deliberately.

14Retries must not leave half a locale in the real resource treeShould fix

In plain English

The plan writes a locale and only afterward discovers bad keys. If retries still fail, the repository can be left with a mixture of good and unresolved output.

Why it matters

The next run or a careless commit can mistake partial generated files for a completed locale.

Plan correction

Generate into a temporary staging directory, validate everything, then replace that locale’s files in one final step. On failure, preserve only the run report.

15The pilot languages are stripped from the APK unless the pilot enables themShould fix

In plain English

German, Arabic, and Japanese are currently marked packaged: false. Gradle removes their resources, and the picker hides them.

Why it matters

You cannot “install and walk the app” in those languages if the built APK does not contain them.

Plan correction

Define a temporary local/debug pilot override, or temporarily enable only those three for the pilot and explicitly revert before the full catalogue flip.

Group 3 · Weblate and ongoing maintenance

Concerns that appear after the one-off seed is finished

The permanent workflow matters more than the one-time batch. These issues would cause confusing diffs, stale percentages, or setup mistakes later.

16A repository translation-status file is unnecessaryDe-scope

In plain English

We do not need a second JSON database saying whether every string is translated.

Why it causes trouble

Weblate already owns translation and review state. A checked-in copy can become stale, disagree with Weblate, and create a new failure unrelated to the app’s actual resources.

Plan correction

Do not split translation_status.json; remove it from the Phase 4 design. Compute coverage from the keys present in each locale XML, and let Weblate show editorial states in Weblate.

17“Completion” must have one explicit meaningShould clarify

Two possible numbers

Coverage means a translated value exists. Review completion means a human approved it. These are not the same.

Current seed decision

The plan marks every successful AI output as translated, so it will display 100% even though a human has not reviewed every sentence.

Recommendation

Call the picker number “translation coverage.” Keep human review state in Weblate. That makes the number honest and computable from the APK’s resources.

18The Weblate alias checklist misses Portuguese (Portugal)Correct mapping

Why are there two names?

They describe the same language, but Android and Weblate speak different naming dialects. Android requires the folder values-pt-rPT; Weblate identifies the language as pt_PT.

Simple analogy

It is like one system using a phone number with spaces and another using the same number without spaces. You need one small conversion at the boundary; you do not need two different languages.

Plan correction

Keep one catalogue as the source of truth, with each system’s required identifier. Generate the boundary mapping automatically, including pt-rPT:pt_PT. The generated list is eight entries, not seven.

19The Android format check is a built-in check, not an add-on to installWording

In plain English

Weblate’s Android resource format automatically enables its Java-format placeholder check.

Why it matters

A maintainer following the checklist may look for an “Android format-check add-on” that does not exist under that name.

Plan correction

Say “verify the built-in Java format check is active.” Keep Cleanup translation files and Squash Git commits in the actual add-on list.

20The APK “before” measurement cannot happen after the locale flipShould fix

In plain English

The execution order flips all locales in step 5 but waits until step 8 to build both “before” and “after.” By then, the real before-state is gone.

Why it matters

Reconstructing the old APK later is easy to get wrong and can mix unrelated build changes into the size difference.

Plan correction

Build and record the filtered baseline immediately before the flip. Build the multilingual APK immediately after it, using the same revision and settings.

21Negative gate tests should use fixtures, not edited production resourcesShould fix

In plain English

The plan suggests deleting a real German key and changing a real status entry to prove failure behavior.

Why it matters

Manual mutation is easy to forget to restore and does not become a repeatable regression test.

Plan correction

Create temporary test fixtures. Prove that malformed translations fail and missing translations report successfully without touching the real locale files.

Recommended rewrite

A simpler Phase 4 execution order

This keeps the useful parts of the original plan and applies your non-blocking translation policy.

1.Define one shared coverage calculator and change CI policy: malformed fails; missing reports and passes.
2.Build the seed tool with a curated glossary, stable output schema, safe IDs, and staging writes. Treat the one-time seed cost as accepted.
3.Pilot German, Arabic, and Japanese with an explicit debug packaging override; validate structure and inspect on device.
4.Run the remaining locales. Omit unresolved keys so Android uses English and Weblate sees untranslated work.
5.Record the pre-flip APK size, package/show all chosen locales, regenerate the picker, then record the post-flip size.
6.Configure Weblate from the catalogue, including all aliases, and make sparse target files the permanent workflow.
7.Expose coverage in the PR summary, picker, and release-job summary. The release report is informational; release creation remains in the Android workflow.
8.Add fixture-based regression tests for fallback reporting and structural failures; print manual device commands without running them by default.
What is already strong

These parts should stay

Keep XML away from the model

Opaque placeholder tokens plus mechanical XML serialization is the right safety boundary.

Keep the de / ar / ja pilot

Those three languages exercise long Latin text, right-to-left and complex plurals, and CJK rendering.

Keep the catalogue as the source of truth

Android qualifiers, picker entries, and Weblate mappings should continue to derive from one locale catalogue.

Keep Android’s sparse-resource fallback

It is exactly what allows product work and translation work to move at different speeds.

Keep structural translation validation

Placeholder, plural, XML, and non-translatable leakage checks protect runtime correctness without demanding 100% coverage.

Keep release automation separate

The Android workflow may print translation health during a release, but the report never decides whether the release is allowed.
